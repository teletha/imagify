imagify.webp.jna

WebpLibrary

  • com.sun.jna.Library

JNA binding for the C ABI in src/main/native/webp/imagify_webp.h.

It is a binding for that header and not for libwebp itself. libwebp's C API is public and has no error callbacks, so a binding could in principle name WebPEncode directly, and doing that has two problems it avoids.

Structures. Encoding a picture means filling in struct WebPPicture, which is 256 bytes on a 64 bit platform and mostly not data: it is the padding libwebp reserves for itself, a union of three sample pointers, a statistics block it may write through, and four function pointers. A binding would have to name every one of those fields and get every offset right, and a mistake in any of them is not a compile error but a wild pointer write while a picture is being encoded. The animation API cannot be driven without one either, since it takes a WebPPicture per frame. The layout is declared as "private fields, padding for later use" in encode.h, so there is no upstream promise to hold a mapping of it to. None of it crosses this boundary: the shim keeps it on the C side, and what crosses is plain scalars, pointers and buffers.

Names. libwebp's own names are exactly the ones a system libwebp also claims, and this jar has no reason to interoperate with one. The bundled library is named imagifywebp and exports only the imagify_webp_* entry points, so a second copy of libwebp in the process cannot be the one that answers a call.

Every byte[] that crosses this boundary is tightly packed A, B, G, R: the byte at offset 0 of a pixel is its alpha and the byte at offset 3 is its red. That is the order a java.awt.image.BufferedImage#TYPE_4BYTE_ABGR raster keeps its banks in, because such a raster declares band offsets of 3, 2, 1, 0 even though java.awt.image.Raster#getDataElements reports the very same sample as R, G, B, A.

The native library is not loaded by this interface; see WebpCodec for the lazy, failure tolerant loader.

LIBRARY_NAMEString

Name of the shared library as this jar builds it.

Deliberately not webp. libwebp builds libwebp.so, which is also the name of every system libwebp on Linux, and two of those can end up mapped in one process. This jar has no reason to interoperate with a system libwebp, so the bundled library is given a name of its own.

ABI_VERSIONString

The version of the C ABI this binding was written against, as IMAGIFY_WEBP_ABI_VERSION in src/main/native/webp/imagify_webp.h spells it.

It is checked once when the library is loaded and nothing else depends on it, because the only way it could ever be wrong is a library built against a different revision of the header, and that has to be caught before the first call rather than after it has written through a pointer read from the wrong offset.

DEFAULT_QUALITYint

Quality used when the caller does not ask for one: 75, the libwebp default.

The number is the one imagify.ImageFormat.Webp carries as its 0.0 to 1.0 defaultQuality, restated on the encoder's own 0 to 100 scale. That is the same thing imagify.avif.jna.AvifLibrary#DEFAULT_QUALITY and imagify.jpeg.jna.JpegliLibrary#DEFAULT_QUALITY do: a codec cannot read a package private member of the format that describes it, so each one says what it does by default and the format's own value follows it. Restating it rather than copying it into two call sites is what keeps the two from drifting apart.
