imagify.webp.jna

WebpCodec

Entry point to the libwebp based WebP codec.

This is the encoder and decoder behind both the ImageIO service providers in imagify.webp and the direct calls imagify.ImageWriter and imagify.ImageReader make, so a WebP written through any of them comes out of the same encoder with the same settings.

The native library is loaded lazily, on first use, and failing to load it is never fatal: the ImageIO service providers of this library then stay inert instead of breaking ImageIO for every other format, and the facade falls back to the JDK's own WebP support, which is the javax.imageio providers that ship with a JDK 13 or newer. Use #isAvailable() to find out which of the two a given call will use.

Prebuilt shared libraries for Windows, macOS and Linux, in both 64 bit flavours, ship inside this jar and are unpacked on demand, so installing anything is not required. Should this jar hold no library for the current platform, a libwebp based one found the usual way is used instead: point the jna.library.path system property (or the platform specific PATH / LD_LIBRARY_PATH) at the directory that holds it. 

 java -Djna.library.path=/usr/local/lib -cp ... YourApp

Set -Dimagify.webp.bundled=false to ignore the bundled library and always look for one installed on the system.

Images are always converted to the tightly packed A, B, G, R layout the native library imports and exports, through the shared AbgrPixels, so an unassociated alpha channel survives without being premultiplied against an opaque background and a fully transparent pixel keeps the colour underneath it. Decoded stills are handed out as the standard BufferedImage#TYPE_INT_ARGB or BufferedImage#TYPE_INT_RGB types, with the alpha type chosen by whether the file carries an alpha channel.

Reads the container headers of a WebP file without decoding the pixels.

For an animation the frame count and the loop count come from the animation decoder, because the still image headers do not carry them. That makes this call as expensive as decoding an animation, so the ImageIO reader calls it once and caches the answer.

Reports which of the two bitstreams a WebP file stores its pixels in, from the container alone.

A still image names its bitstream in the first chunk of the file, VP8L when it is lossless and VP8 when it is lossy. An animation is an extended file whose frames carry a bitstream of their own, so the first frame is the one that is looked at; a file that mixes the two is reported as its first frame has it. A container that says neither before the data runs out is reported as lossy, which is what #FORMAT_VP8L is not.

Unlike #readHeader(byte[]) this needs no native library and decodes nothing, which is what makes it usable while only a format is being detected, before any pixel has been looked at. Only the first #losslessHeaderLength() bytes are read, so a caller that has a shorter prefix than that is answered from what it has.

losslessHeaderLength()int

int

Reads a WebP file and decodes its frames in one pass.

Prefer this over #readHeader(byte[]) followed by a decode when the frames are wanted anyway, which is the case for every ImageIO read. #readHeader(byte[]) stays the cheaper choice for a still image inspected for its size alone, because it decodes no pixels.
