AvifShim

The imagify_avif_* entry points of the C shim, which is what makes the zero copy possible.

The shim is a thin C ABI over libavif that exists for one reason. avifRGBImage.pixels is a pointer-typed struct field, and FFM will not put a heap segment, which is what a Java array is, into one: the field is a pointer into native memory that the struct itself lives in, and a pointer to the Java heap has neither the lifetime nor the alignment the struct would then be promising. An encode that fills that field from Java therefore has to copy the pixels into native memory first, and the copy is of a whole image.

A function parameter is a different matter. A call reaches the callee with Option#critical(boolean) set, which pins the array for the length of the call rather than copying it, and the shim's entry points take the pixels that way. The callee is on the stack for the length of the call and cannot store the pointer anywhere that outlives the pin, so the array does not have to be native memory to be safe. That is the whole of the shim, and everything else it does is so that no libavif struct has to be described in Java.
