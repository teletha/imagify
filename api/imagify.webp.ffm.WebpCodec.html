imagify.webp.ffm

WebpCodec

Entry point to the libwebp based WebP codec using Java's Foreign Function & Memory API (JEP 454).

This is the encoder and decoder behind both the ImageIO service providers in imagify.webp and the direct calls imagify.ImageWriter and imagify.ImageReader make, so a WebP written through any of them comes out of the same encoder with the same settings.

The native library is loaded lazily, on first use, and failing to load it is never fatal: the ImageIO service providers of this library then stay inert instead of breaking ImageIO for every other format, and they fall back to the JDK's own WebP support, which is the javax.imageio providers that ship with a JDK 13 or newer. Use #isAvailable() to find out which of the two a given call will use.

Shared libraries for Windows, macOS and Linux, in both 64 bit flavours, are fetched on first use from the GitHub release the codec's native.properties names, and are cached locally, so installing anything is not required. Should none be available for the current platform — an unsupported one, an unpublished release, a blocked download — a libwebp based one found the usual way is used instead: point the java.library.path system property (or the platform specific PATH / LD_LIBRARY_PATH) at the directory that holds it. 

 java -Djava.library.path=/usr/local/lib -cp ... YourApp

Set -Dimagify.webp.bundled=false to ignore the managed library and always look for one installed on the system.

Images are always converted to the tightly packed A, B, G, R layout the native library imports and exports, through the shared AbgrPixels, so an unassociated alpha channel survives without being premultiplied against an opaque background and a fully transparent pixel keeps the colour underneath it. Decoded stills are handed out as the standard BufferedImage#TYPE_INT_ARGB or BufferedImage#TYPE_INT_RGB types, with the alpha type chosen by whether the file carries an alpha channel.

Encodes an image, choosing how hard the encoder tries.

method is libwebp's own effort scale and runs against #MIN_METHOD and #MAX_METHOD. Lower is faster and produces a larger file, and the difference is large enough to be worth naming: on a 1600x1200 photograph, method 0 takes roughly a quarter of the time method 4 does and gives up about a third more bytes. Neither end is wrong and the choice is a caller's, which is why the default of is only a default and not a fixed point.
