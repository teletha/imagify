AvifConstants

The AVIF_* constants this binding names, taken from avif.h at tag v1.4.2.

They are here rather than in AvifShim because they are values and not entry points, and because the shim is otherwise a wall of downcall handles with nowhere to put a constant that belongs to neither the calls nor the blocks of answers.

Every value here is the one the header of libavif 1.4.2 gives, and each group says which C enumeration it is reading, because a bare number in a call site is not something a reader can check against the header. The groups are the header's own: the pixel formats, the three CICP enumerations, the encoder's quality and speed ranges, the upsampling filters, the status codes this layer defines, and the positions the shim answers at.

Nothing here is libavif's own idea of a default unless it says so. #DEFAULT_SPEED, #DEFAULT_QUALITY and #DEFAULT_ANIMATION_SPEED are numbers this project chose on a measurement, and each one says which; #AVIF_SPEED_DEFAULT is libavif's, and it is kept beside them precisely because it is not the same thing and is a trap when it is mistaken for one.

RGB_FORMAT_ABGRint

AVIF_RGB_FORMAT_ABGR: the byte at offset 0 of a pixel is its alpha and the one at offset 3 is its red.

This is the format the whole zero copy is arranged around, and the reason is imagify.pixels.AbgrPixels: that is the order a BufferedImage of type TYPE_4BYTE_ABGR keeps its banks in, so a picture already in that layout can be handed over without a shuffle. The formats that read as R, G, B, A would swap red and blue in both directions, and would not fail while doing it.

AVIF_SPEED_DEFAULTint

AVIF_SPEED_DEFAULT: leave the AV1 codec at its own speed settings.

Negative, and that is not a placeholder. It is a legal value a caller may pass to mean "whatever libavif thinks", and it is not what this library encodes with by default: measured on a 517x380 photograph against libavif 1.4.2, it is indistinguishable from #AVIF_SPEED_SLOWEST and costs 4917 ms against 170 ms at #DEFAULT_SPEED, for a file of the same size. It is a legitimate answer to give and a terrible one to default to.

AVIF_SPEED_SLOWESTint

AVIF_SPEED_SLOWEST: the most thorough, and the slowest.

AVIF_SPEED_FASTESTint

AVIF_SPEED_FASTEST.

DEFAULT_SPEEDint

The speed a still image is encoded at when the caller did not name one.

This is not libavif's #AVIF_SPEED_DEFAULT and it is not #AVIF_SPEED_SLOWEST either, both of which are what an unqualified "default" would suggest. It is a number this project chose, on a measurement: at 517x380 and quality 70 the encode is 170 ms at speed 6 against 4917 ms at speed 0, and the two produce a file of the same 77 kB. Speeds 8 and 10 are faster still and give up more than they save, so 6 is where the curve flattens.

DEFAULT_QUALITYint

The quality a still image is encoded at when the caller did not name one.

libavif's AVIF_QUALITY_DEFAULT is -1, which is an absence rather than a number, and an absent quality is not something to hand a codec that will happily invent one. 60 is a choice, and it is a mid one: it is a little above the point where AVIF stops being visibly worse than the source and well below the point where the file stops being smaller.

DEFAULT_ANIMATION_SPEEDint

The speed an animation is encoded at when the caller did not name one.

An animation pays the encoder cost once per frame, so the speed that is a fair trade for a single image is a bad one for a hundred of them. Measured on the 58 frame 498x280 test animation at quality 70, going from #DEFAULT_SPEED to this value took the encode from **6556 ms to 436 ms** and made the file smaller, **574 kB to 413 kB**, at the same time. Being faster and smaller at once is unusual enough to be worth stating twice, because it is the whole argument for this value over the still image default.

8 rather than 9 or 10 because the size flattens here: 9 and 10 are both 414 kB, so what they buy over 8 is about 50 ms and 1 kB in the wrong direction.

THREADING_PIXEL_THRESHOLDint

The number of images decoded as a rough threshold above which threading is worth handing to libavif, and below which it is not.

A thousand threads' worth of setup is not free, and the conversion a decode ends in is a single pass over the picture, so a small image is faster on one thread. The threshold is the same one the JNA binding it replaces used, and it is in pixels rather than in bytes because that is what decides how much work there is.
