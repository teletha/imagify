imagify.avif.ffm

AvifCodec

AVIF encoding and decoding, bound to libavif through a C shim and the Foreign Function & Memory API.

Neither side of the boundary moves a pixel. The pixels of a picture on the way in are the caller's own array, handed to AvifShim#pictureFromAbgr as a heap segment, which the linker passes through as a pointer and the shim reads without copying. On the way out they are one buffer the shim allocated, read once into the image it becomes. The JNA binding this replaces made two copies of every decoded picture, the second of them into the very data buffer the image is made of, because a DataBufferByte cannot be handed an array that already exists.

There is a C shim here, unlike for a binding that can talk to a library's C API directly, and it exists for the one thing FFM will not do from Java. A heap segment, which is what a Java array becomes, cannot be stored into a pointer-typed struct field, and avifRGBImage.pixels is exactly such a field. A function parameter is not a struct field, so an entry point that takes the pixels as its own argument has no such restriction, and that entry point is the shim.

Loading is lazy and failing to load is never fatal; see AvifLoader and #getUnavailableReason().

readHeader(byteencoded)AvifImageInfo

byteencoded

the complete AVIF file
AvifImageInfo

the image properties, of which hasAlpha is not one
AvifException

Reads the properties of an AVIF file's container without decoding a pixel.

A sequence is opened and its first frame is described, but no frame is walked and no plane is allocated, so this costs a header parse and nothing else. A file that is a still is a sequence of one, so it answers the same way.

One field of the answer is not real: AvifImageInfo#hasAlpha() always reads false here. Whether a file carries alpha is a property of the alpha plane, and the alpha plane is only allocated when a frame is decoded, so a header parse has nothing to look at. libavif does not surface the sequence header's alpha flag separately. Use #decode when the answer matters, and treat this one as unknown rather than as false.

Encodes a sequence of frames as an animated AVIF file with explicit subsampling and chroma downsampling filter.

A setting that is -1 is an absence rather than a value, and libavif's own choice is made in its place: AvifConstants#DEFAULT_ANIMATION_SPEED for the speed, AvifConstants#QUALITY_LOSSLESS for the alpha quality, AvifConstants#PIXEL_FORMAT_YUV420 for an animation, and AvifConstants#CHROMA_DOWNSAMPLING_AUTOMATIC for the filter.

The frames are packed into one block before they are handed over, and that block is read where it lies: the whole point of the shim's animation entry point is that a hundred frames are not copied a hundred times on the way in.

isAvif(bytedata)boolean

bytedata

the leading bytes of a file, at least 12 of them
boolean true when the data looks like an AVIF file

Tests whether the given bytes are an AVIF file by looking for the avif or avis brand in the leading ftyp box.

The check is pure Java and therefore also works when the native library is missing, which is what lets the ImageIO plug-in still recognise AVIF files.
